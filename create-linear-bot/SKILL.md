# Create Bot

Scaffolds a Linear-to-GitHub Actions agent bridge: Linear comments mentioning `@<bot> <verb>` trigger Claude Code Action via a Cloudflare Worker, with a centralised identity config and a sync script for renames. The canonical implementation in this repo is `@pasha`.

The verb vocabulary is: `plan`, `go`, `ideate`, `investigate`, `review`, `continue`, `stop`, `help`, `details`, `status`, `prompt`. See [Verb behaviour](#verbs).

## When to use

- A Linear workspace needs an agent that responds to `@<bot> <verb>` commands
- Adding the verb-router pattern (plan / go / review / ideate / investigate / continue / stop / help / details) to a different repo
- Renaming an existing bot built with this pattern (see [Renaming the bot](#renaming-the-bot))

## When NOT to use

- Slack-only bots with no GitHub Actions backing — different architecture
- One-shot CLI scripts that don't need a webhook
- Auto-review-on-PR-open workflows that don't need verb routing — those use `.github/workflows/claude-code-review.yml` directly
- Renaming a bot built with a *different* architecture — this skill assumes the `bot.config.json` + `sync-bot.mjs` pattern

## Architecture

```
Linear comment "@<bot> <verb>"
  → Linear webhook (Comment.create)
  → Cloudflare Worker
       ├─ verifies HMAC signature
       ├─ self-trigger guard (skips bot-authored comments)
       ├─ inline handlers for help / details / status (post directly, no GH roundtrip)
       └─ POST repository_dispatch on GitHub
  → GitHub Actions verb router (.github/workflows/<bot>.yml)
       ├─ help / details / status / stop fast-paths (no Claude tokens)
       └─ agent job → Claude Code Action
            ├─ Claude reads ticket + writes plan / findings / answer to `<bot>-output.md`
            ├─ "Post output to Linear" step: workflow itself curls Linear API with file content
            └─ "Move Linear ticket to In Review" step: only on `go`, only when PR opened
```

Inline-handled verbs (`help`, `details`, `status`, `stop`) bypass GitHub Actions entirely — instant response, $0 Claude cost. `prompt` is a thin verb — same agent runtime, but Claude is told to answer concisely without writing code or opening a PR.

### Verbs

| Verb | Effect | Inline? | Posts back via |
|---|---|---|---|
| `plan` | Step-by-step implementation plan | No | File handoff |
| `go` | Branches, codes, opens PR | No | PR (via Linear↔GitHub sync) + auto-status to "In Review" |
| `ideate` | 2-3 alternative approaches | No | File handoff |
| `investigate` | PostHog/Sentry/Vercel findings | No | File handoff |
| `review` | Inline PR review comments | No | GitHub PR review API |
| `continue` | Resumes interrupted run | No | File handoff |
| `prompt <text>` | One-off Q&A | No | File handoff |
| `help` | Static command list | Yes (worker) | Worker posts inline |
| `details` | Full docs | Yes (worker) | Worker posts inline |
| `status` | Health check | Yes (worker) | Worker posts inline |
| `stop` | Cancel in-flight runs | Effectively (workflow only cancels, no Claude) | gh API |

## Step-by-step creation

For each step, **read the reference impl in this repo first** before writing the new file. This saves reinventing already-debugged details.

1. **`bot.config.json`** at repo root with `{ "name": "...", "triggerPhrase": "@..." }`
2. **`services/<bot>-bridge/`** — copy `services/claude-linear-bridge/` wholesale, then:
   - Update `package.json` `name` and `description`
   - Update `wrangler.toml` `name` (Cloudflare Worker subdomain) and `[vars]` for the new repo
   - `src/config.ts` and `src/index.ts` are identity-free — they read from `bot.config.json` — so usually no changes needed
3. **`.github/workflows/<bot>.yml`** — copy `.github/workflows/claude.yml`. The trigger phrase is parameterised via `bot.config.json`-derived regex inside the parse step's `github-script`. Update only if multi-bot in same repo.
4. **`scripts/sync-bot.mjs`** — copy as-is if single-bot. Multi-bot needs generalisation (out of scope for this skill).
5. **Root `package.json`** — add `"sync-bot": "node scripts/sync-bot.mjs"` and `"bot:redeploy": "pnpm sync-bot && pnpm --filter <bot>-bridge redeploy"`.
6. Run `pnpm sync-bot` once to generate `.claude/commands.md` and `.claude/commands-detailed.md`.
7. Do the [External setup](#external-setup) below.

## External setup (human-only steps)

These can't be automated by an agent — only the human can do them:

### Linear
- Create OAuth application: `https://linear.app/<workspace>/settings/api/applications/new`
  - Callback URL: `https://<bot>-bridge.<your-cloudflare-subdomain>.workers.dev/oauth/callback`
  - Scope: `read,write`
  - Public: No
- Register webhook: Settings → API → Webhooks → New webhook
  - URL: same Worker URL (no `/oauth/callback` suffix)
  - Resource types: **Comments** only
  - Action types: **Create** only
  - Linear shows the signing secret on creation — save it for the next step

### Cloudflare Worker secrets

```bash
cd services/<bot>-bridge
pnpm exec wrangler login
pnpm exec wrangler secret put LINEAR_WEBHOOK_SECRET     # from the webhook step above
pnpm exec wrangler secret put LINEAR_OAUTH_CLIENT_ID    # from the OAuth app
pnpm exec wrangler secret put LINEAR_OAUTH_CLIENT_SECRET
pnpm exec wrangler secret put GITHUB_TOKEN              # fine-grained PAT, Contents:write only
pnpm exec wrangler deploy
```

Then visit `https://<bot>-bridge.<subdomain>.workers.dev/oauth/start` in a browser, click **Authorize**, copy the access token shown, and:

```bash
pnpm exec wrangler secret put LINEAR_OAUTH_TOKEN
```

### GitHub Secrets

In the target repo's Settings → Secrets and variables → Actions:

- `CLAUDE_CODE_OAUTH_TOKEN` — auto-installed by the Anthropic GitHub App (`/install-github-app` from a Claude Code session)
- `LINEAR_API_TOKEN` — set to `Bearer <oauth-token>` (**with the literal `Bearer ` prefix** — the workflow's `curl` passes this directly as the `Authorization` header, so missing the prefix causes silent 401 failures)

**Token map — which secret is which:**

| Secret | Where | Format | Used for |
|---|---|---|---|
| `LINEAR_OAUTH_TOKEN` | Cloudflare Worker | raw token (no prefix) | Worker posting ack comments and help/details/status responses |
| `LINEAR_API_TOKEN` | GitHub Actions | `Bearer <token>` (with prefix) | Workflow curl posting final output back to Linear |
| `LINEAR_OAUTH_CLIENT_ID` | Cloudflare Worker | raw | OAuth PKCE flow |
| `LINEAR_OAUTH_CLIENT_SECRET` | Cloudflare Worker | raw | OAuth PKCE flow |
| `LINEAR_WEBHOOK_SECRET` | Cloudflare Worker | raw | HMAC signature verification |
| `GITHUB_TOKEN` | Cloudflare Worker | raw PAT | `repository_dispatch` trigger |

> **`wrangler secret put` applies instantly** — no redeploy needed. The running Worker picks up the new secret on its next invocation. `pnpm exec wrangler deploy` is only required when you change `wrangler.toml` or the Worker source code itself.

## Hard rules — non-negotiable gotchas

We hit each of these the first time around. Don't repeat.

1. **Self-trigger guard is mandatory.** The bot's own help/details/status content contains `@<bot> <verb>` examples. Without `actor.type` + body-prefix checks, posting help triggers a real plan run, which posts a plan, which is itself a comment, which... loops. Implementation lives in `isBotAuthored()` in `services/claude-linear-bridge/src/index.ts`. We hit this incident on WEB-556 — don't ship without the guard.

2. **`allowed_tools` and `max_turns` are NOT valid `anthropics/claude-code-action@v1` inputs.** They get silently ignored with a warning. Pass them inside `claude_args` as CLI flags: `claude_args: "--model ... --max-turns 100 --allowed-tools Read,Edit,Write,Bash,Glob,Grep"`. Use a high `--max-turns` (100) so complex `go` runs don't get truncated mid-implementation; `@<bot> stop` is the kill switch.

3. **`pnpm/action-setup` + `setup-node` with `cache: pnpm` only run for verbs that install** (`go`, `continue`). For other verbs the cache directory never gets populated and the post-job cleanup fails the whole job. Use a job-step `if: needs.parse.outputs.verb == 'go' || needs.parse.outputs.verb == 'continue'`.

4. **Use file handoff, NOT in-agent curl, for posting output back to Linear.** The action's sandbox permission-denies Claude's `curl` to external hosts (visible as `permission_denials_count > 0` in the run summary). Don't ask Claude to call the Linear API itself — instead:
   - Prompt instructs Claude to write final output to `<bot>-output.md` at the repo root
   - A workflow step (after `Run Claude`) reads the file and `curl`s the Linear `commentCreate` mutation directly using the workflow runtime (no sandbox restrictions)
   - Step is gated on `verb in {plan, ideate, investigate, continue, prompt}` AND `linear_issue_id != ''`
   - **Add `<bot>-output.md` to `.gitignore`** so writes during a `go`/`continue` run that mistakenly produce the file don't get committed
   - We hit this incident on WEB-579 — Claude generated a plan that never reached Linear because curl was blocked

5. **Worker passes `parentId` on `commentCreate`** so the bot's reply is threaded under the trigger comment. If the trigger is itself a reply (has `parentId`), use the trigger's parent (Linear only supports one level of nesting).

6. **OAuth `actor=app` requires `&actor=app` in the authorize URL.** Personal API tokens authenticate as the human who created them — the bot will post comments as that human. Use OAuth for clean app attribution. **Linear doesn't always allow renaming an OAuth app** — if you want a different display name later, you may have to create a new OAuth app and swap the Worker's `LINEAR_OAUTH_CLIENT_ID` / `LINEAR_OAUTH_CLIENT_SECRET` / `LINEAR_OAUTH_TOKEN` secrets, then revoke the old one.

7. **Status auto-update on `go`.** Add a workflow step after `Run Claude` that calls Linear's `issueUpdate` mutation with the team's "In Review" state UUID when verb is `go` and the agent succeeded. Skipped for other verbs to avoid pulling tickets backwards (e.g. `plan` shouldn't move a Done ticket back to In Progress). State UUIDs differ per Linear team — look them up via `mcp__linear-recash__list_issue_statuses` or hardcode in the workflow.

8. **Inline-handled verbs (`help`, `details`, `status`)** must be in the worker's `KNOWN_VERBS` AND have explicit `if (verb === '...')` early-return branches in the webhook handler. Without the early return, they'd dispatch to GitHub for nothing. Their content lives in `config.ts` constants — `STATUS_MESSAGE` is hardcoded, `HELP_CONTENT` and `DETAILS_CONTENT` are imported from `.claude/commands*.md` via wrangler text bundling.

9. **`prompt` verb extracts the user's question from `rest`.** The parse step strips `--opus` and `--approach` flags from the comment body's tail, then injects what remains as `## User's question` in the prompt. Easy to miss when adding new flags.

10. **MCP OAuth plugins (`posthog@claude-plugins-official`, `sentry@claude-plugins-official`) cannot authenticate in GitHub Actions.** These plugins use a browser-based OAuth callback flow — they only expose `authenticate` and `complete_authentication` tools, and there is no way to complete the browser redirect step in a headless CI environment. Adding them to the workflow causes silent tool failures. Use API-key-based MCP servers instead (e.g. `mcp-linear@latest` with a raw `LINEAR_API_KEY` env var) or inject observability data via the prompt using curl/API calls before the agent runs. We confirmed this when attempting to add PostHog and Sentry MCP plugins to the workflow — they are only usable interactively in a Claude Code desktop session.

## Verification

After the External setup is done, walk these in order:

1. **`@<bot> status`** → `✅ <Bot> is online and listening.` within ~1s. Confirms the webhook → bridge → reply roundtrip works without invoking GitHub Actions.
2. **`@<bot> help`** → command card threaded under the trigger. **Exactly one response** — if you also see `🧠 ... is drafting a plan…`, the self-trigger guard is broken.
3. **`@<bot> plan`** on any ticket → ack `🧠 <Bot> is drafting a plan…` within 1s, then a real plan reply within a few minutes. Confirm the GitHub Actions run shows a green `Post output to Linear` step (file-handoff working).
4. **`@<bot> prompt how does <something> work`** → ack `💬 <Bot> is thinking…`, then a written answer. Confirms the prompt verb's question-extraction is correct.
5. **`@<bot> go`** on a small ticket with a prior plan → PR opens, ticket auto-moves to "In Review" in Linear.
6. **`pnpm exec wrangler tail`** shows clean signature verifications. No `Invalid signature` errors.
7. **The Linear comment author is the OAuth app**, not a human user (confirms `actor=app` token).
8. Inspect a recent run: `gh run view <id> --log | grep permission_denials_count` — should be `0`. If `> 0`, Claude tried to do something blocked (most often: curl). Re-check that the prompt uses the file-handoff pattern, not curl-from-Claude.

## Renaming the bot

```bash
# 1. Edit bot.config.json:
#    { "name": "Newname", "triggerPhrase": "@newname" }

pnpm sync-bot       # regenerates auto-gen docs + find-replaces previous identity in other docs
pnpm bot:redeploy   # syncs + redeploys the Worker
```

Notes:
- **Linear OAuth apps cannot be renamed** — Linear does not expose a rename UI. To change the displayed comment author name, you must **create a new OAuth app**, complete the OAuth flow to get a new token, update all three Cloudflare secrets (`LINEAR_OAUTH_CLIENT_ID`, `LINEAR_OAUTH_CLIENT_SECRET`, `LINEAR_OAUTH_TOKEN`), then revoke the old app. The Worker URL doesn't change, so no webhook reconfiguration is needed.
- **`wrangler secret put` applies instantly** — no `wrangler deploy` needed. The running Worker picks up new secrets on the next request.
- Avatar is uploaded to the OAuth app in Linear, not stored in code. Re-upload after creating a new app.
- Webhook config does NOT change — the Worker URL is unchanged.
- The sync script tracks the previous identity by parsing the auto-generated `.claude/commands.md` (its `# <Name> — Commands` line). No separate state file.
